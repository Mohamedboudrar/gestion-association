# Frontend Summary

## Tech Stack

- **Framework**: React 19.2.7
- **Routing**: React Router DOM 7.18.1
- **Styling**: Tailwind CSS 4.3.2
- **HTTP Client**: Axios 1.18.1
- **Icons**: Lucide React 1.24.0 (react-icons is also installed but unused — Lucide is the actual icon set throughout)
- **Charts**: Recharts 3.9.2
- **Build Tool**: Vite 8.1.1
- **Linting**: oxlint 1.71.0
- **Internationalization**: i18next 26 + react-i18next 17 + i18next-resources-to-backend 1.2 — the entire UI is rendered through translation keys (`t('namespace:key')`), never hardcoded strings. French is the only language (no switcher, no detection); strings still live in per-namespace JSON so the app stays consistent and re-extendable. See Internationalization (i18n) below.
- **Bulk expense import**: `exceljs` (XLSX read/write) + `papaparse` (CSV parse) — see Key Features. `exceljs` was picked over the more common `xlsx`/SheetJS npm package specifically because the npm-published `xlsx` build has two known unpatched HIGH severity CVEs (prototype pollution, ReDoS) that matter here since this code parses attacker-uploaded files; `exceljs`'s own moderate-severity transitive `uuid` advisory is in a code path this app never exercises. `exceljs`'s CSV support depends on Node's `fs`/streams and doesn't work in a browser bundle, hence pairing it with `papaparse` for the CSV half.
- **Project location map**: `@tomtom-international/web-sdk-maps` + `@tomtom-international/web-sdk-services` — see Key Features and `components/maps/`. Both packages are npm-deprecated in favor of `@tomtom-org/maps-sdk` and carry moderate/high transitive `lodash`/`uuid` advisories (`npm audit`) with no non-breaking fix available; kept anyway since the task named these exact packages explicitly. They're map-rendering/search SDKs, not something that parses untrusted user-uploaded files (unlike the `xlsx` case above), so the risk profile is different — worth revisiting if TomTom ships a maintained successor.

## Routing & Navigation

`App.jsx` defines every real route. A `moduleRoutes` array at the bottom renders `ModulePlaceholderPage` for paths **not** already matched by an explicit `<Route>` above it — `/members/board`, `/financial-operations`, `/settings/security` are the only paths that actually fall through to the placeholder today (everything else in that array, e.g. `/members`, `/donations`, `/reports`, is shadowed by a real route and the placeholder entry for it is dead code). `/settings` moved from this fallback list to a real `<Route>` (`SettingsPage`) this session — see Association Settings below.

Navigation is **not** a simple président/everyone-else split — `PresidentLayout.jsx` picks one of three navigation sets based on the logged-in user's role, from `config/presidentNavigation.js`:

- **`presidentNavigation`** (static, **restructured into workspace-shaped groups this session** — previously a flat per-resource list) — Overview (Dashboard) → **Association** (Subscribers, Projects, Committees) → **Finance** (Finance Overview, Donations, Expenses) → **Approvals** (Subscription Payments, Expense Approvals, Phase Requests, Deletion Requests — carries a live pending-count badge on the section label itself, `badgeKey: 'approvals'`, computed by `PresidentLayout` from the single consolidated `GET /action-center` endpoint (the same `getActionCenter()` call the dashboard's `ActionCenter` card uses — see the `ActionCenter` component under Components below, and Action Center in `backend/BACKEND_SUMMARY.md`), summing **4 of its 5** pending counts: `subscriptions + expenses + phase_requests + deletion_requests`, deliberately **excluding** `donations`) → Reports → **Administration** (Activity Logs, Settings). **Receipts and the full subscription-payment history no longer have their own sidebar entries at all** — both are reachable as header buttons on `FinancePage` instead (see below); "Pending Payments"/"Pending Expense Approvals"/"Pending Phase Requests" were consolidated into the one Approvals group instead of being scattered across their own resource's section, and "Deletion Requests" (previously missing from the sidebar entirely) was added there too.
- **`buildBureauNavigation(user)`** (dynamic, for vice-president/trésorier/vice-trésorier/secrétaire général/vice-secrétaire général/conseiller) — Overview, Members, Subscriptions, Projects (+ **Committees** and **Pending Phase Requests** only if `canAssignCommittee`, i.e. vice-president — same role tier as `ProjectPhaseRequestPolicy`'s review authority), Reports, a Finance section (Finance + Donations + **Expenses** + **Pending Expense Approvals**) only for trésorier/vice-trésorier (`isTreasurerRole`) — matches who the backend's `ExpensePolicy::APPROVAL_ROLES` actually lets approve/reject/mark paid — and an **Administration → Activity Logs** entry for every bureau role unconditionally (the backend scopes what actually shows: president/vice-président/trésorier see every activity, every other bureau role only their assigned projects', possibly none — see the Activity Explorer section below). **Not restructured into the same grouped shape as `presidentNavigation`** — left as-is, out of scope for the sidebar-reorg pass, which was scoped to the president's own nav.
- **`buildSubscriberNavigation()`** (for plain `abonne`) — Dashboard, "My Subscription" (self-scoped server-side), "My Projects" (self-scoped server-side). Always shows both, even with zero records — `GET /me` doesn't carry project-assignment data synchronously, and an honestly-empty list is a fine result. **No "My Donations" item** — a subsequent session removed one after finding it exposed donor names/individual records; see "App Unification" → "Donation access correction" below. Notifications/Profile aren't repeated in this array — the sidebar footer already renders them for every signed-in user regardless of nav set.

**`FinancePage`'s header** now carries two outlined buttons — **Payment History** (`/subscriptions`) and **Receipts** (`/subscriptions/receipts`) — since the sidebar reorg above removed both from the nav tree; the routes/pages themselves are untouched, just reached differently.

The Account section at the bottom of the sidebar (avatar, name, role, Profile, Logout) is the same for every role — only Profile links out; there's no Settings/Security link since those routes are unimplemented placeholders.

`ProtectedRoute` only checks authentication, not role — role-based visibility is handled entirely by which nav set a user gets plus per-page/per-button capability checks (see `lib/roles.js` below). A user who knows a URL can still hit any route directly; pages that need a hard gate (e.g. `FinancePage`, `ReportsPage`) redirect with `<Navigate>` themselves rather than relying on the nav being hidden.

**`/member` is the one route outside `ProtectedRoute`** (like `/login` — you can't gate a login page behind "must already be authenticated"), but it's no longer a separate mini-app: submitting the passkey form calls `useAuth().loginWithPasskey()`, the exact same `AuthContext` every bureau login goes through, and redirects to `/dashboard` like any other login. There is no `/member/dashboard` anymore — see "App Unification" below.

## `lib/roles.js` — the capability system

This file is the single source of truth the frontend uses to decide what to show, and every exported function is commented with which backend permission/policy method it mirrors — when the backend authorization changes, this file needs to change with it, not the other way around.

- **`getUserRoles`, `hasRole`** — read Spatie role names off the `user` object from `/api/me`.
- **`isBureauMember(user)`** — the 7 non-`abonne` roles; mirrors `AuthorizationHelper::isBureauMember()` on the backend exactly (kept in sync deliberately).
- **`isTreasurerRole(user)`** — tresorier or vice-tresorier.
- **`getCommitteeRole(user, project)`** — reads `project.members[].committee_role` for the current user; requires the full project object (with its `members` array) — a project's *nested* summary (e.g. `donation.project` which is just `{id, name}`) doesn't carry enough data for this and must be resolved against a fully-fetched project first.
- Global capability functions (each named after and matching one backend permission grant): `canCreateMember`, `canEditMemberRecord`, `canDeleteMember`, `canManageProjects`, `canAssignCommittee`, `canRemoveCommitteeMember`, `canVerifySubscription`, `canCreateSubscriptionEntry`, `canUploadSubscriptionReceipt`, `canViewReports`.

## `lib/duesGrouping.js`

`buildDueGroups(dues, subscriptions)` — pure presentation grouping for the subscriber's due-centric Annual Dues view (`SubscriberDuesOverview`, see Components above). ## Key Features

### Internationalization (i18n)

The entire UI renders through translation keys — every user-facing string is `t('namespace:key')`, never a hardcoded literal in a component. Configured in **`src/i18n.js`** (imported once in `main.jsx` before the app mounts).

- **French-only, on purpose.** `LANGUAGE = 'fr'` is the only language: no language switcher, no browser-language detection, `supportedLngs: ['fr']`, `fallbackLng: 'fr'`. Strings still live in JSON (not inlined in components) so wording stays consistent across surfaces and the app is easy to re-extend if a second language is ever wanted — but nothing today toggles locale. This is why the app copy is French throughout (matching the project spec) yet there's no settings toggle for it.
- **11 per-namespace JSON files** under `src/locales/fr/` — one namespace per feature area (`common`, `dashboard`, `association`, `finance`, `approvals`, `reports`, `notifications`, `profile`, `settings`, `pdf`, `validation`), exported as the `NAMESPACES` array. `defaultNS: 'common'`. Kept small and topic-scoped so a page pulls only what it needs.
- **Lazy-loaded via Vite** — `i18next-resources-to-backend` wraps a dynamic `import(\`./locales/${language}/${namespace}.json\`)`, so each namespace JSON is its own code-split chunk fetched on demand rather than one upfront bundle. `react: { useSuspense: true }` — components consuming a not-yet-loaded namespace suspend until its chunk resolves (so pages are wrapped in `<Suspense>` upstream).
- **Usage**: components call `useTranslation([...namespaces])` and reference keys as `t('dashboard:president.title')` (or a bare key against `defaultNS`). Interpolation uses `{{var}}` (e.g. `t('dashboard:subscriber.expires', { date })`) with `escapeValue: false` (React already escapes). Pluralization uses i18next's `_one`/`_other` suffix convention (e.g. `projectMap.withLocation_one`/`_other`).
- **Display-label helpers layered on top** (see Custom Hooks above): `useStatusLabel()`/`useRoleLabel()` map raw backend `status`/`role` values to French labels via the `common` namespace's `status.*`/`roles.*` keys (with `defaultValue` = the raw value, so an unmapped status degrades to showing itself rather than a missing-key string); `useLocaleFormat()` handles `fr-FR` date/number formatting. Together these keep every surface showing the same wording and formatting for the same underlying value.
- **Backend copy too**: the `pdf` and `validation` namespaces mirror French strings the backend also emits (report letterheads, validation messages) — see `backend/BACKEND_SUMMARY.md`. The frontend copies aren't the enforcing source for those, just the client-side rendering of the same French wording.

This feeds `ProjectResource.collected`/`allocated` — it does **not** change `project.budget` (that field is only ever set at creation or via a direct `PUT /projects/{id}` edit). Every project workspace and the committee dashboard surface the resulting ledger read-only.

### Project Lifecycle
New this session. Projects now progress through 6 stages: `draft → committee_ready → funding_ready → active → completed`, plus `cancelled` from any non-terminal stage. `committee_ready`/`funding_ready` happen automatically (first committee assignment / first fund allocation) — there's no button for them. `active` needs an explicit **Start Project** click (shown only once `funding_ready`, gated by `canStartProject`); `completed` needs the existing **Close Project** click (now only shown/allowed while `active`). Donations and expenses can only be created once a project is `active`; fund allocations can be recorded starting at `committee_ready`. `CommitteeProjectPage` shows a stage banner explaining what's needed next for any pre-active project, and `ProjectsPage`/`FinancePage` show a stage badge (Draft/Committee Ready/Funding Ready/Active/Completed/Cancelled) instead of the old raw `planned`/`active`/`completed`/`cancelled` status string. See `lib/projectLifecycle.js` above and `backend/BACKEND_SUMMARY.md`'s Project Lifecycle section for the full state machine — the frontend gates are UX-only, the backend enforces every transition and stage requirement independently.

### Project Closure Reports
Président or a project's committee leader can close it from `CommitteeProjectPage` (Close Project button, header). The backend generates a PDF closure report and a `ProjectReport` row as part of closing, and notifies the project's committee plus bureau roles. The same page's new Reports tab lists and downloads past closure reports for that project. Closing (or cancelling) also dissolves the committee — see below — and the project becomes fully read-only.

### Project Hard Lock
Completed/cancelled projects become read-only association-wide, not just on one page. `isProjectLocked(project)` (`lib/roles.js`) mirrors the backend's `Project::isLocked()` and gates every create/edit/delete/upload/assign/submit/approve/reject/mark-paid control across `CommitteeProjectPage`, `CommitteesPage`, and `FinancePage`; a "Project {status} - read only" banner shows on the project workspace. This is a defense-in-depth/UX nicety — the backend enforces the same lock independently on every write endpoint regardless of what the frontend shows.

### Committee Assignment Lifecycle & History
`CommitteesPage` now has **Active Members** and **Committee History** sub-tabs per project. Active Members gained **Replace** (swap one member for another in the same seat, inline form) and self-service **Resign** (shown only on your own row) alongside the existing Remove (which now asks for a reason). Committee History renders the full, never-deleted assignment ledger as a timeline (date/member/action badge/actor/reason) — every past assignment, replacement, resignation, removal, and project-closure dissolution is visible, not just the current roster.

### Subscription Expiration
A daily backend job (see `backend/BACKEND_SUMMARY.md`) auto-expires verified subscriptions past their `expires_at`. The frontend reflects this with a distinct "Expired" badge on `SubscriptionsPage`, and — with zero extra frontend logic needed — an expired-only member is automatically excluded from `CommitteesPage`'s assignment dropdown, since `MemberResource.has_verified_subscription` is computed fresh from the database on every request.

### Annual Dues

New — a per-member, per-year billing ledger layered on top of Subscriptions, not a replacement for it (see `backend/BACKEND_SUMMARY.md`'s Annual Dues section for the full model/state-machine design). The frontend footprint is deliberately small: no new page, no new route, no new nav entry — the whole feature surfaces inside three existing pages plus one dashboard card, matching the "reuse existing subscription/payment pages" scope this feature was built to.

- **`ProfilePage`** — a new Dues History section (Year/Amount Due/Paid/Remaining/status) below the existing Account Information card, sourced from `getMemberDashboard()`'s new `dues_history` field — reuses the same self-scoped endpoint every account (bureau or subscriber) already had access to, just reads one more field off it.
- **Dashboard** — one new `DuesOverview` card (Expected/Collected/Outstanding/Overdue Members/Collection Rate for the current year), reading `dashboard.dues` off the same `GET /dashboard` response `useDashboard()` already fetches — no new request, no new hook.
- **No dedicated "Dues" page or nav entry was built** — a bureau-facing `GET /dues` (with `member_id`/`year`/`status` filters) and `GET /dues/{id}` exist on the backend for future use, but nothing in the current frontend calls them beyond the two integration points above; the Waive action posts directly to `/dues/{id}/waive` without ever listing dues generally.
- **Sidebar Approvals badge** (see Routing & Navigation above) does **not** include due-related counts — it's scoped to the same 4 pending-queue endpoints it always was (subscriptions/expenses/phase-requests/deletion-requests); overdue dues aren't a "pending approval" in the same sense (there's nothing to approve, just money owed), so surfacing them there would have been a scope mismatch, not a straightforward addition.

### Expense Approval Workflow
Expenses go through `draft → pending → approved/rejected → paid` instead of being created and immediately final. A committee leader/treasurer creates a draft and submits it; only president/tresorier/vice-tresorier can approve or reject (never their own expense); only an approved expense can be marked paid; a decided expense (approved/rejected/paid) can no longer be edited or deleted. `CommitteeProjectPage`'s Expenses tab and the association-wide `ExpensesPage` (`/expenses`, `/expenses/pending`) both surface a status badge and the relevant action buttons per row, sharing the same `ExpenseWorkflowActions`/`RejectReasonModal` components so the rules can't drift between the two surfaces.

**Only approved and paid expenses count toward money** — a project's `expenses`/`remaining` totals (project cards, Finance page, dashboard, PDF/XLSX reports) are all backend-computed off `Expense::FINANCIALLY_COUNTED_STATUSES = ['approved', 'paid']`, never a raw sum of every expense row. The few places that sum a raw client-side expense array — `lib/dashboardMetrics.js`'s `computeAvailableFunds`/`computeMonthlyFinancials` and `CommitteeDashboardPage`'s expense total — filter through `isFinanciallyCountedExpense()` (`lib/expenseStatus.js`) for the same reason. Draft, pending, and rejected expenses never move money.

**Rejecting requires both a reason and a rejection type** — `RejectReasonModal` now has a required type picker (Invoice issue / Expense details issue) alongside the reason textarea, and passes both to `onReject(id, reason, rejectionType)` → `rejectExpense(id, reason, rejectionType)`. The type drives two different post-rejection flows, both gated in `lib/roles.js` and `ExpensePolicy` (kept in sync — see above):
- **Invoice issue** (`rejection_type: 'invoice'`) — `CommitteeProjectPage` still shows the normal "Replace Invoice" upload control (now also allowed on this specific state) and `ExpenseWorkflowActions`'s Submit button reappears labeled **"Submit Again"** (same `POST /expenses/{id}/submit` call, rejected → pending). The same expense row is reused; nothing new is created.
- **Expense details issue** (`rejection_type: 'details'`) — no invoice/edit/delete controls show at all (the expense is fully read-only). Instead `CommitteeProjectPage` shows a **"Create New Expense"** button that prefills the create form (`beginNewExpenseFromRejected`) with the old expense's fields as a convenience — submitting it posts a genuinely new `draft` expense via the existing `POST /expenses`, leaving the rejected one untouched in history.

### Donation Approval Workflow
Deliberately mirrors the Expense Approval Workflow above — same statuses minus "paid" (`draft → pending → approved/rejected`), same components reused rather than copied where the shape matches: `RejectReasonModal` now takes an optional `rejectionTypes` prop (defaults to the expense Invoice/Details pair) so `DonationWorkflowActions` passes its own Receipt-issue/Donation-details-issue pair through the exact same modal — one component, two vocabularies, never two modals to keep in sync. `DonationStatusBadge`/`lib/donationStatus.js` are a parallel (not shared) file pair to `ExpenseStatusBadge`/`lib/expenseStatus.js` — same color values for the statuses both share, kept as separate small files rather than merged since the two domains have different status sets (no "paid") and the codebase's established convention (subscriptions, expenses) is one small dictionary per domain, not one shared generic status system. `DonationWorkflowActions` is a structural copy of `ExpenseWorkflowActions` (same button styles/icons/layout) minus Mark Paid, wired to the new `canSubmitDonation`/`canApproveDonation`/`canRejectDonation`/`isDonationApprovalRole` helpers in `lib/roles.js`, which never approve/reject the recorder's own donation (`donation.recorded_by.id !== user.id`), mirroring `ExpensePolicy`'s creator-restriction exactly. Both `CommitteeProjectPage`'s Donations tab and the association-wide `DonationsPage` (`/donations`) surface a status badge, the workflow action buttons, and — replacing the old ad hoc "All/With Receipts/Assigned to Projects" filter — the same status-tab-with-live-counts pattern `ExpensesPage` already used. `canEditDonation`/`canDeleteDonation`/`canUploadReceipt` now all take the donation itself as a third argument and gate on its status (draft/pending only for edit/delete; draft/pending/rejected-with-receipt-issue for the receipt upload), matching `canEditExpense`/`canDeleteExpense`/`canUploadInvoice` exactly.

**Only approved donations count toward money** — a project's `collected`/`remaining` totals (project cards, Finance page, dashboard, PDF/XLSX reports) are all backend-computed off `Donation::FINANCIALLY_COUNTED_STATUSES = ['approved']`, never a raw sum of every donation row. The client-side places that sum a raw donation array — `lib/dashboardMetrics.js`'s `computeAvailableFunds`/`computeMonthlyFinancials`/`computeFinanceSummary`/`groupDonationsByProject`/`topDonors` and `CommitteeDashboardPage`'s donation total — filter through `isFinanciallyCountedDonation()` (`lib/donationStatus.js`) for the same reason; `computeProjectFunding` needed no change since it already reused the backend-computed `project.collected` rather than re-summing. Draft, pending, and rejected donations never move money. `DonationsPage.jsx`'s own ledger shows every status (not filtered, still carrying `DonationStatusBadge` per row so a pending/rejected entry is never mistaken for a counted one) — but see "Donation access correction" above: that page is bureau financial-oversight only, not a subscriber-facing view.

**Rejecting requires both a reason and a rejection type** — same `RejectReasonModal` flow as expenses, with `Receipt issue` (`rejection_type: 'receipt'`) → **Replace Receipt** + **Submit Again** (same donation row, rejected → pending) versus `Donation details issue` (`rejection_type: 'details'`) → fully read-only, **Create New Donation** prefills the create form (`beginNewDonationFromRejected` / `beginNewFromRejected`) from the old donation without touching it.

### Project Phase Approval Workflow
New this session — replaces the cosmetic "execution %" (a budget-utilization ratio previously shown as if it were execution progress) with a real, verified 5-phase workflow: `planning → preparation → in_progress → finishing → completed`. The committee leader can never set the phase directly — they submit a request (target phase, required summary, optional notes, ≥1 required proof file image/PDF) from `CommitteeProjectPage`'s new **Phases** tab; only one request can be pending per project at a time, and it must target exactly the next sequential phase (no skipping, no going backward). Only a president/vice-président can approve or reject it, from the new association-wide `PendingPhaseRequestsPage` (`/phase-requests/pending`) — approving updates the project's phase and stamps the reviewer/date; rejecting requires a reason and leaves the phase unchanged. `completed` is never requestable — it's set automatically, alongside `status: completed`, by the existing Close Project flow (untouched otherwise). See `lib/projectPhase.js` above and `backend/BACKEND_SUMMARY.md`'s Project Phase Approval Workflow section for the full state machine.

### Project Access Control (security fix)

The frontend never enforced this (nor should it have to — hidden buttons/routes were never the real gate), so the fix is entirely backend-side: see `backend/BACKEND_SUMMARY.md`'s Project Access Control section. What changed here:

- **"Browse Projects" no longer browses every project for subscribers.** `GET /projects` used to return every project (full financials/committee included) to any `abonne` account; it now scopes a subscriber to only projects they're an actual committee member of, same as everywhere else. A subscriber with no committee assignment now sees an empty list on `ProjectsPage` — this is the correct, intended behavior post-fix, not a bug, but it's a real, visible product change from before (previously subscribers really could browse every project's full detail from this page, which was itself the vulnerability).
- No frontend code changes were needed for `ProjectsPage`'s own logic (`isOnCommittee`/`canOpen` gating on the "Open" link) — it already only shows the link for rows the user could actually open, and the list itself is now correctly pre-filtered server-side, so nothing was rendering incorrectly here, just potentially *too much* was in the list before.

### Bulk Expense Import
`CommitteeProjectPage`'s Expenses tab can import a `.csv`/`.xlsx` file of expenses (Import button, plus Download Template in both formats) instead of entering them one at a time. Each row becomes a draft; a review modal walks through them one at a time (reusing the same expense form component used for manual entry), and validates each before "Save All" is enabled. **"Save All" is now atomic** — `handleSaveAllImports` posts the whole batch in one request to the new `POST /expenses/import` (`importExpenses(projectId, drafts)`, `expenses.api.js`) instead of looping `createExpense()` per row. This replaces the previous sequential-loop behavior, which had no atomicity: a failure partway through left every earlier row already created as a real draft, with no way to undo it short of deleting them by hand (the old code even tracked a `createdCount` specifically to explain this to the user — "Earlier drafts in this batch were already created"). Now either every row is created or none are; on rejection (see Expense Budget Validation below) `importDrafts` is left completely untouched so the user can just adjust and retry Save All, no cleanup needed.

### Bulk Expense Delete
New this session. The Expense List (same tab as above) gets a per-row checkbox and a header "select all" checkbox, so a committee leader/treasurer can clean up several draft/pending expenses at once instead of deleting them one at a time. A checkbox only renders for a row where `canDeleteExpense(user, committeeScope, expense) && !locked` is true (approved/rejected/paid expenses, and anything on a locked project, were never deletable and still show no checkbox) — "select all" only ever selects/deselects that same deletable subset. Once at least one row is checked, a **Delete Selected (N)** button appears in the list header; clicking it confirms once (`window.confirm`, same pattern as every other destructive action in this app) and then deletes every selected expense via `Promise.allSettled` over the existing single `DELETE /expenses/{id}` endpoint — no new bulk-delete backend endpoint was added, since (unlike the budget import above) there's no shared invariant across the batch that needs atomicity; each delete is independent. If some deletions fail, the successful ones are gone, the failed ones stay checked, and an inline message reports the split ("3 of 5 expenses deleted. 2 could not be deleted.") so the user can just retry.

### Expense Budget Validation
New this session — a project's `budget` field is now an enforced spending ceiling, not just a display number. Before any expense is created, imported, or edited, the backend recomputes `draft + pending + approved + paid` across that project's other expenses, adds the new/edited amount, and rejects if the total would exceed `project.budget` — see `backend/BACKEND_SUMMARY.md`'s Expense Budget Validation section for the full formula and why `paid` is included even though it wasn't in the task's own literal status list. This is a **second, independent check** from the pre-existing "remaining funds" validation (money actually collected via donations/allocations) — both must pass; they can fail for different reasons on the same request (a project with `$0` collected funds will always fail the funds check regardless of budget headroom).
- **Manual create/edit** (`ExpenseFormFields`'s underlying `createExpense`/`updateExpense` calls, unchanged call sites) — a budget-exceeding request now comes back as a `422` with a descriptive `errors.amount` message including all 5 numbers (Project Budget/Already Allocated/Remaining Budget/New Total/Exceeded By); the existing inline error-rendering already shows whatever string the backend returns, so no new UI was needed here, just a better message.
- **Bulk import** (see above) — a budget-exceeding batch comes back as a structured `422` (`{ message, budget: { project_budget, already_allocated, remaining_budget, new_total, exceeded_by } }`, not just a string), which `handleSaveAllImports` formats into one readable line using `formatCurrency` for every figure — shown in the same `importError` banner the page already had for parse errors.

### Expense Invoice Preview & Filtering
`ExpensesPage` (`/expenses`, `/expenses/pending`) is a master-detail view: an expense list on the left, the selected expense's invoice previewed on the right (PDF embed, zoomable image, or a graceful "no invoice"/"unsupported type" message), with keyboard Up/Down navigation and Prev/Next buttons. A status filter (tabs with live counts) and a project filter (dropdown) combine together, entirely client-side against the already-loaded list — see the Pages table above for the full behavior.

## Known Gaps / Notes

- **`API_CONTRACT.md` is partially stale, partially fixed** — its Subscriptions section was corrected (it used to claim `SubscriptionResource` omits `payment_method`/`receipt_number`/`receipt_file`/`notes`; the live resource already includes all of them, only `verified_by` is actually omitted). A second, separate stale claim persists further down the same file (the "Frontend Integration Notes" section, ~line 936: "Subscription responses include member.user, verifier, verified_by, and verified_at") — left untouched, out of scope for the task that fixed the first one. Treat the live backend resources (see `backend/BACKEND_SUMMARY.md`) as the source of truth over this doc until that second claim is also corrected.
- **Role visibility is UI-only, not a security boundary** — `ProtectedRoute` doesn't check role, so a subscriber could navigate directly to `/finance` or `/reports`; both of those specific pages redirect themselves, but not every page does (`ExpensesPage` included — it relies entirely on the backend's own per-request authorization/data-scoping, same as most other pages). The real security boundary is always the backend policy; frontend gating exists to avoid showing controls that would 403, not to enforce access.
- `getCommitteeRole` and everything built on it silently returns "not a committee member" if the caller passes a project object that lacks a `members` array (e.g. a nested `donation.project` summary) — `DonationsPage` explicitly re-resolves the full project from an already-fetched `projects` list before calling these helpers; this pattern needs to be repeated for any new page that does the same kind of per-row gating. `ExpensesPage`'s workflow actions sidestep this entirely by not needing committee-role data at all (approve/reject/mark-paid are global-role checks, not per-project ones).
- `CommitteeDashboardPage`'s "Allocated to date" column fires one `GET /projects/{id}/allocations` request per assigned project (no bulk endpoint exists) — fine at current project counts, would need a batched backend endpoint to scale.
- **`lib/dashboardMetrics.js`'s `computeAvailableFunds()` is a second, independent "Available Funds" calculation** — it powers only the president Dashboard's `ExecutiveKPIs` card (`funds.balance` = client-summed verified subscriptions + donations − expenses, no allocations involved at all) and is completely disconnected from the backend's authoritative `GET /dashboard` → `available_funds` field that `FinancePage` uses. The two numbers can legitimately disagree — this violates "one source of truth" for available funds but wasn't unified, since doing so would mean reworking the KPI card's caption text too (which currently describes the client formula's own breakdown), not just swapping one number. It was, however, brought in line with the approved-only expense rule this session: `computeAvailableFunds`/`computeMonthlyFinancials` now filter expenses through `isFinanciallyCountedExpense()` before summing, so it no longer counts draft/pending/rejected expenses against the balance — it can still disagree with the backend figure on the allocations point, just not on the expense-status point anymore.

If a future check on this page needs a user's `committee_role`, prefer `committeeScope` for consistency with the rest of the file.
